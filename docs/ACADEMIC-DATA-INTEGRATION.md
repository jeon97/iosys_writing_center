# 학사정보 연계용 데이터 모델과 뷰 설계

글쓰기 시스템이 대학 학사 DB를 직접 해석하지 않도록 연계 전용 뷰의 계약을 정리했습니다. 대학마다 다른 원본 테이블을 그대로 받으면 로그인, 강좌, 수강생 조회 로직이 기관별로 갈라지기 때문에 필요한 정보만 표준 뷰로 제공받는 방식으로 구성했습니다.

## 설계 과정

초기 협의안은 관리자·교수, 학생, 교과, 강좌, 수강 정보를 각각 분리한 5개 구조였습니다. 실제 연동에 필요한 조회를 다시 확인한 뒤 다음 3개 뷰로 줄였습니다.

| 뷰 역할 | 필요한 정보 | 사용처 |
|---|---|---|
| 사용자 | 연도, 학기, 로그인 ID, 이름, 권한, 학년 | SSO 이후 사용자 확인 |
| 강좌 | 과목 코드·명, 연도, 학기, 담당교수 ID·명 | 교수의 담당 강좌 조회 |
| 수강 | 과목 코드·명, 연도, 학기, 학생 ID·명 | 강좌별 학생 동기화 |

원본 학사 스키마의 학부·학과·전공 구조는 글쓰기 시스템이 직접 조합하지 않습니다. 대학 측이 강좌 코드와 분반을 포함한 연계 키를 만들고, 시스템은 그 키를 기준으로 강좌와 수강생을 연결하도록 책임을 나눴습니다.

## 설계 기준

- 비밀번호, 연락처, 이메일처럼 글쓰기 기능에 필요하지 않은 개인정보는 뷰에서 제외
- 학생과 교수 권한 코드를 하나의 사용자 계약으로 통일
- 연도와 학기를 키에 포함해 동일 강좌 코드의 학기 간 충돌 방지
- 강좌 뷰와 수강 뷰의 강좌 코드는 같은 규칙으로 생성
- 필수 컬럼, 타입, 코드값, 예시를 정의서에 함께 제공
- 원본 테이블 변경은 대학 내부에서 흡수하고 연계 뷰 계약은 유지

## 동기화 흐름

```text
기관 학사 DB
  └ 연계 전용 VIEW
      ├ 사용자 → 로그인/권한 갱신
      ├ 강좌   → 담당교수와 강좌 갱신
      └ 수강   → 강좌별 학생 갱신
                    └ 없는 관계 비활성화
```

동기화는 사용자, 강좌, 수강 순서로 실행합니다. 한 단계가 실패하면 다음 단계를 실행하지 않아 존재하지 않는 사용자나 강좌를 참조하는 수강 관계가 생기지 않도록 했습니다.

[공개용 SQL 예제](../samples/database/academic_views.sql)는 실제 기관명, 테이블명, 코드 체계를 제거하고 위 설계 판단만 재작성했습니다.
